# v2.4 — ラップタイム取りこぼしの解消（UART溢れ・ESP-NOW再初期化・送信リトライ）

### 🐞 修正：ラップタイムが時々ゴーグルのOSDに表示されない

ラップタイムは（毎秒再送されるレースクロックと違い）**1回きりの送信**のため、
ブリッジ内で1回失われるとそのラップは二度と表示されませんでした。
調査の結果、Wrover（ESP-NOWブリッジ）側に取りこぼしの窓が複数見つかりました。

- **UART受信バッファを 256B → 2048B へ拡張**（v2.3 の XIAO 側と同じ対策を Wrover 側にも適用）。
  `SET_SEND_UID` 処理中は MAC 変更 + ESP-NOW 再初期化で `loop()` が数十ms止まり、
  その間に届く1ラップ分 300B 超の OSD バーストが既定バッファから溢れていました。
- **同じ UID なら ESP-NOW 再初期化をスキップ**。
  従来は `SET_SEND_UID` のたびに `esp_wifi_set_mac` + deinit/init を実行しており
  （1ラップで最大4回、レースクロックで毎秒）、再初期化中の送信は失われていました。
  適用済み MAC をキャッシュし、UID が変わったときだけ再初期化します。
- **ESP-NOW 送信リトライを実装**。
  `esp_now_send` は fire-and-forget で、ACK が得られなかったパケットは捨てられていました。
  送信を TX キュー経由に変更し、失敗時は最大3回まで自動再送。
  UID 切り替え時はキューを掃いてから切り替え、旧 UID 宛パケットの宙吊りを防止します。

### 🛡 修正：MSPパーサのバッファオーバーラン（両ファームウェア共通）

UART でバイトが欠落するとヘッダがずれて payload 長がゴミ値になり、
64B の payload バッファを越えて書き込んでメモリ破壊（=不定動作・リセット）を
起こす可能性がありました。

- payload 長がバッファ超過のパケットは破棄して再同期するよう修正。
- `addByte()` にも境界ガードを追加。
- `elrs-espnow-bridge` / `elrs-xiao-webui` 両方の MSP ライブラリに適用。

### ✅ 動作確認

実機での書き込み・レース運用テストに合格。
あわせてホスト環境でのロジックテスト19項目（再初期化スキップ／リトライ／
タイムアウト回復／パーサ再同期など）にすべてパス。
